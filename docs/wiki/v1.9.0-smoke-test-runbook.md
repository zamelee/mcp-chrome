# v1.9.0 Smoke Test Runbook

**Purpose**: collect real-world heartbeat telemetry from mcp-chrome v1.9.0 to verify the chrome.alarms 30s watchdog path works under realistic conditions (idle SW, multiple tabs, laptop sleep/wake cycles).

**Duration**: 30 minutes (background, no special action needed)

**Prerequisites**: mcp-chrome v1.9.0 installed (Chrome Web Store or Load Unpacked from `.output/chrome-mv3`).

---

## Step 1: Open Chrome DevTools to capture telemetry

1. Open Chrome → `chrome://extensions` → find mcp-chrome → click "service worker" link
2. This opens DevTools for the extension background SW
3. Go to **Console** tab
4. (Optional) Filter by `[telemetry]` to see only heartbeat events — or `[bridge-control]` for full SW logs

You should see lines like:

```
[telemetry] {"type":"heartbeat","source":"setInterval","scheduledAt":...,"firedAt":...,"delayMs":1200,"ownerId":"...","isStale":false,"buffered":42}
[telemetry] {"type":"heartbeat","source":"alarm","scheduledAt":...,"firedAt":...,"delayMs":50,"ownerId":"...","isStale":false,"buffered":43}
```

`source` distribution should be ~50/50 between `setInterval` and `alarm` (both fire every 30s; alarm catches up when SW is alive).

## Step 2: Use Chrome normally for 30 minutes

Do whatever you normally do. The point is to let mcp-chrome run in the background while:

- You open/close tabs
- You navigate to sites
- You may go idle (SW freezes)
- You may close/reopen the laptop

You do **not** need to drive the extension actively — the telemetry is collected passively.

## Step 3: Capture the console output

After 30 minutes, in DevTools Console:

1. Right-click → "Save as..." → save the full console log
2. Or use Cmd+`A` to select all → Cmd+`C` to copy → paste into a file

## Step 4: Send to maintainer

Attach the console log to a GitHub issue:

- Title: `[smoke-test-v1.9.0] <Chrome version> <OS> <date>`
- Body: paste the console log
- Labels: `smoke-test`, `telemetry`

Or send via email / Discord if GitHub is not convenient.

## Step 5: What we look for

Maintainer analyzes:

- **delayMs distribution** for each source:
  - `setInterval`: should be near 30s (30000ms); jitter <1s expected
  - `alarm`: should be near 30s; typical jitter 40-70s worst case (R2 ChatGPT data)
  - `chrome.tabs`: triggers immediately on tab lifecycle events, not periodic
- **ownerId drift**: should remain stable across the 30min unless you reload the extension manually
- **gap between heartbeats**: max gap should be < 60s under any normal usage (proves alarm backs up setInterval)
- **`source:alarm` count**: should be at least 1 even if you never go idle (alarm fires every 30s by design)

If `gap between heartbeats` exceeds 90s under normal usage, we have a watchdog regression — please flag in the issue.

## Optional: Active stress test

If you have time and want to stress the watchdog:

1. Open 5+ tabs and navigate each to a heavy page (e.g. Google Docs, YouTube)
2. Let Chrome sit idle for 5 minutes
3. Verify heartbeat telemetry continues firing throughout

Idle SW freeze was the original bug — this stress test specifically validates the fix.

## Maintainer checklist (private)

When receiving a smoke test report:

- [ ] Heartbeat count > 30 over 30min (= 1/min minimum)
- [ ] max gap < 90s
- [ ] source distribution includes `alarm` (alarm path tested)
- [ ] if user reports "假死" but heartbeat still firing, investigate chrome.alarms listener binding (v1.9 reconcileState should handle it)
- [ ] Update `docs/wiki/v1.9.0-smoke-test-results.md` with anonymized metrics
